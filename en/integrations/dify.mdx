Dify is suitable for workflows, agents, knowledge base, and internal AI application platforms. When integrating with Crazyrouter, it is recommended to first follow Dify’s OpenAI-compatible model vendor path, get the chat model working first, then gradually add Embedding or other functions.

## Overview

With Dify’s model vendor setup, you can use Crazyrouter as an OpenAI-compatible upstream connection:

- Recommended protocol: `OpenAI-compatible API`
- Recommended entry: `Settings / Settings` → `Model Provider / Model Provider`
- Base URL: `https://api.crazyrouter.com/v1`
- Authentication method: `sk-...` token
- Recommended initial model for verification: `gpt-5.5`

<Tip>
In different Dify versions or plug-in releases, the vendor name may show as `OpenAI`, `OpenAI-API-compatible`, `OpenAI Compatible` or similar. Choose the OpenAI-compatible entry that supports customizing `API Base URL`.
</Tip>

<Note>
The official Dify documentation treats custom `API Base URL` as an optional item for proxy or compatible upstream scenarios; when connecting Crazyrouter, treat Crazyrouter as the OpenAI-compatible upstream and fill in `https://api.crazyrouter.com/v1` accordingly. Also, configuring the model vendor usually requires Workspace Admin or Owner rights; if you don’t see the entry, check your current account role.
</Note>

## Usage Protocol

Recommended protocol: `OpenAI-compatible API`

When connecting Crazyrouter in Dify, the typical OpenAI-compatible base address is:

```text
https://api.crazyrouter.com/v1
```

Do not use:

- `https://api.crazyrouter.com`
- `https://api.crazyrouter.com/v1/chat/completions`

<Tip>
In different Dify versions, interface wording may switch between `Model Provider`, `Model Provider`, `Providers`, or plug-in market entries, but keep the initial verification path unchanged: first save the vendor, then add only one `LLM` model `gpt-5.5`, and finally create the simplest Chat application for validation.
</Tip>

## 5-Minute Quick Start

<Steps>
  <Step title="Create a dedicated Dify token">
    In the Crazyrouter backend, create a new token, and name it `dify` as recommended. Initially, only open `gpt-5.5` and one embedding model, for example `text-embedding-3-large`.
  </Step>
  <Step title="Go to model provider settings">
    Log into Dify using an account with workspace admin rights, and go to `Settings / Settings` → `Model Provider / Model Provider`.
  </Step>
  <Step title="Add an OpenAI-compatible provider">
    Select the vendor entry of `OpenAI` or `OpenAI-compatible` type, fill in:
    - `API Key`: your `sk-...`
    - `API Base URL`: `https://api.crazyrouter.com/v1`
  </Step>
  <Step title="First, configure only one chat model">
    Add an LLM first, for example:
    - `Model / Model`: `gpt-5.5`
    - `Type / Type`: `LLM`

    After saving, create the simplest Chat app or Workflow app for validation. Don’t try to add chat, embedding, rerank, and workflow tools all at once, or troubleshooting will get confusing.
  </Step>
  <Step title="Complete the initial verification">
    In the app, send the phrase: `Reply only OK`. If a successful reply is returned and there are logs in Crazyrouter backend, the chat path works. Then add Embedding or other models next.
  </Step>
</Steps>

## Embedding and Knowledge Base Suggestions

If you want to use knowledge base, RAG, or document retrieval in Dify, add embedding models as the second step:

| Use | Recommended Model | Description |
|------|----------|------|
| Default Embedding | `text-embedding-3-large` | More reliable, good for knowledge base starting point |
| Low-cost Embedding | `text-embedding-3-small` | Saves money, suitable for larger scale documents |

Recommended order:

1. Verify chat model first
2. Then verify embedding
3. Finally import knowledge base and optimize recall

Troubleshooting is clearest this way.

## Token Settings Best Practices

| Setting | Recommendation | Explanation |
|------|------|------|
| Dedicated token | Required | Dify should not share tokens with chat frontend or CLI tools |
| Model whitelist | Highly recommended | Only allow models that are actually used in Dify workflow |
| IP restriction | Enable for fixed deployment exits | Use cautiously for frequently switching local development environments |
| Quota limit | Highly recommended | Dify workflows, batch jobs, and knowledge base imports may quickly consume quota |
| Environment separation | Required | Use different tokens for development, testing, and production |
| Chat / Embedding separation | Suggested | For high-traffic scenarios, split into different tokens for easier billing and rate limiting |

## Common Errors and Fixes

| Issue | Common Cause | Fix |
|------|----------|----------|
| Cannot see `Model Provider / Model Provider` entry | Current account is not workspace admin or owner | Use an account with permission or ask admin to configure |
| Vendor entry visible, but no OpenAI-compatible option | This version made it a plug-in, used different names, or requires enabling the corresponding vendor first | Look for entries like `OpenAI`, `OpenAI Compatible`, `OpenAI-API-compatible`; check plug-ins or version documentation if needed |
| Vendor cannot be saved | API Key error, or vendor type does not support custom Base URL | Use OpenAI-compatible vendor entry and refill `sk-...` |
| 401 unauthorized | Token expired, copied wrong, or deleted | Regenerate token and replace |
| 403 / model not allowed | Model selected in Dify not on token whitelist | Allow the corresponding model in Crazyrouter backend |
| 404 | `API Base URL` written as root domain name or full API path | Change to `https://api.crazyrouter.com/v1` |
| Chat model can be configured but app throws error | Wrong model name, or context parameter misconfigured | Roll back to `gpt-5.5` to verify baseline |
| Knowledge base import fails | Chat model works but embedding model misconfigured | Validate embedding setup separately first, then re-import knowledge base |
| Workflow cost increases quickly | Bulk runs, long context, or multiple apps sharing one token | Split tokens, set quota limits, and narrow down model selection |
| Some advanced model features behave inconsistently in Dify | Parameter compatibility differs for each model in Dify nodes | Get baseline working with `gpt-5.5`, then switch to other models step by step |

## Performance and Cost Recommendations

- Test workflows first with `gpt-5.5`; add other models after stabilizing
- When launching a knowledge base for the first time, import documents in small batches to check recall quality before bulk import
- Account for chat and embedding models separately, making it easier to trace costs
- Set stricter quota limits for batch tasks, scheduled tasks, and internal test environments
- When facing high consumption, check Crazyrouter logs first to see if it’s caused by workflow retries, knowledge base imports, or multiple apps using the same token

## FAQ

### Which Base URL should Dify use?

Use `https://api.crazyrouter.com/v1`.

### Why not just use the root domain?

Because Dify’s OpenAI-compatible model vendor usually requires an OpenAI-compatible base address, not the root domain.

### Should I configure chat or embedding models first?

Configure the chat model first; once apps can return results, add embedding next.

### Can Rerank models be configured directly?

Depends on your Dify version and available vendor plugins. Run chat and embedding first, then consider whether Rerank needs to be accessed separately.

### Why emphasize configuring only a single chat model first?

Because Dify issues can easily occur across the vendor, model type, app parameters, and knowledge base chain simultaneously. Focusing on a single `gpt-5.5` chat application first makes troubleshooting much clearer.

### Should Dify use multiple tokens?

Yes. Separate development / production at minimum; in high-traffic scenarios, split chat and embedding tokens.

<Note>
Dify is best positioned as an "application platform" and "workflow platform". Compared to chat frontends, it emphasizes process orchestration, knowledge base, and multi-environment management, making dedicated tokens, model whitelists, and quota strategies more essential.
</Note>
