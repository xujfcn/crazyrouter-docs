Coze（扣子）はバイトダンスが提供するインテリジェントエージェント＆ワークフロープラットフォームです。Bot 作成、ワークフローの編成、プラグイン呼び出し、多チャネル公開などに適しています。Crazyrouter を接続する場合、公開ドキュメント向けで最も確実な推奨ルートは「すべてのバージョンがカスタムモデルを利用できる」と仮定せず、まず HTTP / API プラグインやワークフローの HTTP リクエストノード経由で進めることです。

## 結論から先に

ほとんどの Crazyrouter ユーザーにとって、Coze では以下の2つの方法がおすすめです：

- 方法1：`API を基に作成` プラグインを使って Crazyrouter を呼び出す
- 方法2：ワークフロー内の HTTP リクエストノードで Crazyrouter を呼び出す

「Coze モデル管理で Crazyrouter カスタムモデルを直接接続する」方法を公開主要チュートリアルとして記載するのは推奨しません。その理由は：

- Coze のバージョン・地域・プランによって利用可能な機能が大きく異なるため
- Coze の公式プラン説明で、`カスタムモデル` は企業フラッグシップ版の機能と明記されています
- 公開ドキュメントとしては、より安全なのは HTTP / API プラグインルートです

<Warning>
このページで最も重視すべき正確性の原則は、「Coze の公開主要ルートを『HTTP / API プラグインで Crazyrouter を呼び出す』と明記し、すべてのユーザーがモデル管理でカスタム上流を掛けると仮定しない」ことです。
</Warning>

## 適したユーザー

- Coze Bot やワークフローで Crazyrouter を利用したい方
- Crazyrouter を外部モデル呼び出しノードとして使いたい方
- まず最小検証チェーンを作りたい、最初から企業版カスタムモデル機能には進まない方
- Bot からプラグインやワークフローで複数モデル機能へアクセスしたい方

## 推奨接続方法

### 公開主要ルート：HTTP / API プラグイン方式

推奨パラメータ：

- リクエスト方法：`POST`
- URL：`https://api.crazyrouter.com/v1/chat/completions`
- ヘッダー：
  - `Authorization: Bearer sk-xxx`
  - `Content-Type: application/json`
- 最初の検証モデル：`gpt-5.5`

### なぜこの方法を最初に推奨するのか

理由は：

- Coze プラン差異に依存しない
- 「Coze 設定の問題」か「Crazyrouter トークン / モデルの問題」かを簡単に切り分けられる
- 公開文書で安定した説明がしやすい

## システム要件と事前条件

| 項目 | 説明 |
|------|------|
| Crazyrouter アカウント | [crazyrouter.com](https://crazyrouter.com) で登録 |
| Crazyrouter トークン | Coze 用にトークンを個別作成するのが推奨 |
| Coze アカウント | Bot / ワークフロー / プラグインの作成権限が必要 |
| 公開権限 | Bot やワークフローのデバッグが最低限できること |
| 利用可能モデル | チャットモデルが最低1つ開放されていること |

推奨初期ホワイトリスト：

- `gpt-5.5`
- `claude-opus-4-8`
- `gemini-3.1-pro`

## 方法1：API プラグインで Crazyrouter 接続

<Steps>
  <Step title="ステップ1：Crazyrouter で Coze 専用トークンを作成">
    初回は以下のみ開放推奨：

    - `gpt-5.5`
    - `claude-opus-4-8`

    最初から多くのモデルを開放しない方が、トラブルシュートが容易です。
  </Step>

  <Step title="ステップ2：Coze で API プラグインを作成">
    Coze のワークスペースに入り、現在のバージョン画面で：

    - `プラグイン`
    - `プラグインを作成`
    - `API を基に作成` または近い名称の入口を選択

    <Note>
    Coze の画面名称はバージョン・地域・製品ラインによって多少違うことがありますが、基本的な考え方は「外部 HTTP API プラグインを作成する」ことです。
    </Note>
  </Step>

  <Step title="ステップ3：リクエスト方法と URL を設定">
    記入：

    - `Method`: `POST`
    - `URL`: `https://api.crazyrouter.com/v1/chat/completions`
  </Step>

  <Step title="ステップ4：リクエストヘッダを設定">
    記入：

    ```text
    Authorization: Bearer sk-xxx
    Content-Type: application/json
    ```
  </Step>

  <Step title="ステップ5：最小リクエストボディを設定">
    初回は最小リクエストボディ推奨：

    ```json
    {
      "model": "gpt-5.5",
      "messages": [
        {
          "role": "user",
          "content": "{{input}}"
        }
      ]
    }
    ```

    プラグイン画面がパラメータマッピングをサポートしている場合、ユーザー入力を `{{input}}` のようなプレースホルダー変数にマッピング可能です。
  </Step>

  <Step title="ステップ6：まずはプラグイン内で接続確認を行う">
    現バージョンがプラグインのデバッグをサポートしていれば、まず以下を送信：

    ```text
    Reply only OK
    ```

    まず安定してレスポンスを返すことを確認し、次に Bot やワークフローに連結しましょう。
  </Step>

  <Step title="ステップ7：Bot またはワークフロー内でプラグインを呼び出す">
    プラグイン単体テストが通ったら、以下へ追加：

    - Bot のプラグイン機能
    - もしくはワークフローノード

    最初はプラグインに簡単なタスクのみ担当させるのがおすすめです（例：要約、リライト、固定Q&Aなど）。
  </Step>
</Steps>

## 方法2：ワークフロー HTTP リクエストノードで Crazyrouter 接続

プラグイン単独管理をしたくない場合は、ワークフロー内で HTTP リクエストノードを直接使って呼び出しも可能です。

### 推奨設定

- リクエスト方法：`POST`
- URL：`https://api.crazyrouter.com/v1/chat/completions`
- ヘッダー：
  - `Authorization: Bearer sk-xxx`
  - `Content-Type: application/json`
- ボディ：

```json
{
  "model": "gpt-5.5",
  "messages": [
    {
      "role": "user",
      "content": "{{input}}"
    }
  ]
}
```

### 推奨検証順序

1. ノード内で固定文字 `Reply only OK` を送信
2. その後、変数入力を試す
3. 最後に出力を次ノードへマッピングする

## 「カスタムモデル接続」の理解について

Coze の一部バージョンやプランではカスタムモデル接続が可能な場合もありますが、Crazyrouter 公開ドキュメントの主ルートとして採用すべきではありません。

理由：

- Coze 公式プラン FAQ では `カスタムモデル` が企業フラッグシップ版機能と明記されています
- 一般ユーザーにとって公開再現しやすく検証しやすいのはやはり HTTP / API プラグイン方式
- このページではカスタムモデル機能は補足背景でのみ記載し、公開教育の標準ルートとして明記しません

## 推奨モデル設定

| 利用シーン | 推奨モデル | 理由 |
|----------|----------|------|
| 初回チェーン検証 | `gpt-5.5` | 2026年3月23日実環境で成功実績あり、Coze→Crazyrouter の呼び出しチェーン検証に最適 |
| 高品質出力 | `claude-opus-4-8` | より強力な解釈・内容生成に最適 |
| Gemini バックアップ | `gemini-3.1-pro` | 2つ目の互換検証ルートとして推奨 |

## トークン設定ベストプラクティス

| 設定 | 推奨 | 説明 |
|------|------|------|
| 専用トークン | 必須 | Coze はデスクトップクライアント・IDEツールとトークン共用は禁止 |
| モデルホワイトリスト | 強く推奨 | 初回は1～2モデルのみ開放 |
| クオータ上限 | 強く推奨 | ワークフローのループやプラグイン再試行で消費量が増加 |
| 環境分離 | 推奨 | dev/test/productionでトークンを分ける |
| 漏洩対応 | 即時ローテーション | プラグインスクリーンショットや共有ワークスペースで露出後は即キー交換 |

## よくあるエラーと修正方法

| 現象 | 主な原因 | 修正方法 |
|------|----------|----------|
| 401 unauthorized | トークンが誤り・期限切れ・一部欠損 | トークンを再作成し `Authorization` ヘッダー再記入 |
| 404 | URLミス、または `/v1/chat/completions` 不足 | URL完全化して修正 |
| 403 / model not allowed | トークンで対象モデル未開放 | Crazyrouter トークン設定でモデル開放 |
| `model not found` | モデル名が間違っている | `gpt-5.5` に戻して再検証 |
| プラグインは作成できるが Botで呼べない | プラグイン入出力マッピング不整合 | 固定文字列でデバッグに戻す |
| ワークフローノードが時々失敗 | 入力が長すぎる・再試行多すぎ・高並列 | 入力縮小・複雑さ削減で最小検証 |
| 他人のチュートリアルで「モデル管理接続」が見つからない | バージョンやプラン違い | HTTP / API プラグイン主要ルートに戻り、まず企業版機能依存は避ける |

## FAQ

### Cozeで Crazyrouter を最も推奨する方法は？

公開ドキュメントでは HTTP / API プラグインやワークフロー HTTP リクエストノード方式が最優先。

### なぜ「カスタムモデル接続」を主ルートにしないのか？

Coze はバージョンやプランによって機能差異が大きく、公式 FAQ にも `カスタムモデル` は企業フラッグシップ版機能と記載。公開ドキュメント向けにはより再現性・ハードルが低い HTTP 方式が適しています。

### URLには何を記入すべき？

`https://api.crazyrouter.com/v1/chat/completions` を記入してください。

### 最初に推奨されるモデルは？

まず `gpt-5.5` を使いましょう。

### Claudeなど追加モデルはいつ追加すべき？

まず単一モデル・単一ノード・単一タスクを正常稼働させてから、段階的にホワイトリストを拡大。

<Note>
目的が「Cozeでまず Crazyrouter を安定呼び出しする」なら、最も大切なのは複雑な接続を追求することではなく、まず HTTP / API プラグインで最小チェーンを確実に通すことです。
</Note>
