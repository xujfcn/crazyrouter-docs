Dify はワークフロー・Agent・ナレッジベース・社内 AI アプリプラットフォームに適しています。Crazyrouter を連携する際は、まず Dify の OpenAI 互換モデルプロバイダー経由を推奨し、チャットモデルを先に連携し、次に Embedding や他の機能を追加していく形がおすすめです。

## 概要

Dify のモデルプロバイダー設定を使うことで、Crazyrouter を OpenAI 互換の上流として接続できます。

- 推奨プロトコル：`OpenAI-compatible API`
- 推奨エントリー：`設定 / 設定` → `モデルプロバイダー / モデルプロバイダー`
- Base URL：`https://api.crazyrouter.com/v1`
- 認証方式：`sk-...` token
- 推奨初回認証モデル：`gpt-5.5`

<Tip>
Dify のバージョンやプラグイン化されている配布版によって、プロバイダー名が`OpenAI`、`OpenAI-API-compatible`、`OpenAI Compatible`などの類似名で表示される場合があります。カスタム `API Base URL` をサポートしているOpenAI互換エントリーを優先して選択してください。
</Tip>

<Note>
Dify公式ドキュメントでは、カスタム `API Base URL` を代理や互換上流の利用例として紹介しています。Crazyrouter を連携する場合は、この OpenAI互換上流として `https://api.crazyrouter.com/v1`を記載しましょう。モデルプロバイダーの設定は通常、ワークスペース管理者またはオーナー権限が必要です。エントリーが見当たらない場合、アカウントの役割を確認してください。
</Note>

## 利用対象

- ワークフロー・Agent・ナレッジベースアプリ構築を目指す方
- チャットモデルやEmbeddingモデルをCrazyrouterに一元接続したいチーム
- 業務部門向けにビジュアルAIオーケストレーションプラットフォームを提供したい方
- テスト・本番環境でモデルを分けて管理したい方

## 利用規約

推奨プロトコル：`OpenAI-compatible API`

DifyでCrazyrouter連携時、通常記入するOpenAI互換Base URLは：

```text
https://api.crazyrouter.com/v1
```

以下は入力しないでください：

- `https://api.crazyrouter.com`
- `https://api.crazyrouter.com/v1/chat/completions`

<Tip>
Difyのバージョンによって、UI文言が`Model Provider`、`モデルプロバイダー`、`Providers`またはプラグインマーケット入口間で切り替わることがありますが、初回認証の流れは変更しないこと：まずプロバイダーを保存し、次に一つの`LLM`モデル`gpt-5.5`だけ追加し、最後に最小構成のChatアプリで認証します。
</Tip>

## 前提条件

| 項目 | 説明 |
|------|------|
| Crazyrouterアカウント | まず [crazyrouter.com](https://crazyrouter.com) で登録 |
| Crazyrouterトークン | Dify専用の`sk-...`トークンの新規作成を推奨 |
| Dify | 最新安定版をおすすめ。バージョンによって呼び方が多少異なる場合あり |
| 利用可能なモデル | テスト済みのチャットモデルを少なくとも一つ、例：`gpt-5.5` |

推奨初回ホワイトリスト：

- `gpt-5.5`
- `claude-opus-4-8`
- `text-embedding-3-large`
- `text-embedding-3-small`

ナレッジベース用途の場合、チャットモデルとEmbeddingモデルの両方を用意しておくことを推奨します。

## 5分間クイックスタート

<Steps>
  <Step title="Dify 専用トークンを作成">
    Crazyrouter管理画面で新トークンを作成、名前は`dify`がおすすめ。初回は`gpt-5.5`とEmbeddingモデル1つ（例：`text-embedding-3-large`）のみ開放。
  </Step>
  <Step title="モデルプロバイダーの設定に入る">
    ワークスペース管理権限のあるDifyアカウントでログインし、`設定 / 設定` → `モデルプロバイダー / モデルプロバイダー`へ進む。
  </Step>
  <Step title="OpenAI 互換プロバイダーを追加">
    `OpenAI`または`OpenAI-compatible`プロバイダーエントリーを選び、以下を記入：
    - `API Key`: あなたの`sk-...`
    - `API Base URL`: `https://api.crazyrouter.com/v1`
  </Step>
  <Step title="まずはチャットモデルだけを設定してください">
    まずはLLMを一つ追加、例：
    - `モデル名 / モデル`: `gpt-5.5`
    - `モデルタイプ / タイプ`: `LLM`

    保存後、最も簡単なChatアプリやWorkflowアプリを作成して認証テスト。チャット、Embedding、Rerank、ワークフローツールを一度に追加しないこと。トラブルが混在します。
  </Step>
  <Step title="最初の認証を完了しました">
    アプリで「`Reply only OK`」を送信。正常応答とCrazyrouter管理画面でログが確認できれば、チャットルートは成功。Embeddingや他モデルはその後追加してください。
  </Step>
</Steps>

## Embeddingとナレッジベース推奨事項

Difyでナレッジベース、RAG、ドキュメント検索を行う場合は、次ステップでEmbeddingモデルを追加することをおすすめします。

| 用途 | 推奨モデル | 説明 |
|------|----------|------|
| デフォルトEmbedding | `text-embedding-3-large` | より安定した品質、ナレッジベース初期に適合 |
| ローコストEmbedding | `text-embedding-3-small` | コスト削減、大規模文書用途に適合 |

推奨順序：

1. チャットモデルを先に認証
2. 次にEmbeddingを認証
3. 最後にナレッジベースインポートと召回チューニング

この順番だとトラブルシュートが明確です。

## 推奨モデル設定例

| 利用シーン | 推奨モデル | 理由 |
|----------|----------|------|
| ワークフロー標準チャットモデル | `gpt-5.5` | テスト済みで、Difyチャットの主軸として適合 |
| 高品質複雑シーン | `claude-opus-4-8` | 複雑な説明や要約、長文により適合 |
| Geminiバックアップ用 | `gemini-3.1-pro` | 上流互換性検証用に適合 |
| デフォルトEmbedding | `text-embedding-3-large` | ナレッジベース品質安定 |
| ローコストEmbedding | `text-embedding-3-small` | 予算重視のインデックス環境向け |

推奨流れ：チャットモデルをまず動かし、その後Embeddingを追加。

## Token設定ベストプラクティス

| 設定 | 推奨 | 説明 |
|------|------|------|
| 専用トークン | 必須 | Difyとチャットフロント・CLIツールでトークン共用しないこと |
| モデルホワイトリスト | 強く推奨 | Difyワークフロー実際に使うモデルのみ許可 |
| IP制限 | 固定デプロイ環境で推奨 | ローカル開発環境では慎重運用 |
| クォータ上限 | 強く推奨 | ワークフロー、バッチ、ナレッジベースインポートで消費が早い場合あり |
|環境分離 | 必須 | 開発・テスト・本番はトークンを分けて運用 |
|チャット/Embedding分離 | 推奨 | 高トラフィック時はトークン分割で課金・制限管理しやすく |

## 認証チェックリスト

- [ ] `モデルプロバイダー / モデルプロバイダー`でCrazyrouter設定を保存済み
- [ ] `API Base URL`が`https://api.crazyrouter.com/v1`に設定済み
- [ ] 少なくとも一つのLLMを追加済み
- [ ] 初回のDifyアプリリクエストで正常応答
- [ ] Crazyrouter管理画面で該当リクエストログ確認
- [ ] ナレッジベース用途時、Embeddingモデル設定済み
- [ ] トークンのクォータ・ホワイトリストが期待通り
- [ ] 開発/テスト/本番でトークン分離運用済み

## よくあるエラーと対処

| 症状 | 主な原因 | 修正方法 |
|------|----------|----------|
| `モデルプロバイダー / モデルプロバイダー`エントリーが見えない | アカウントに管理者/オーナー権限なし | 権限ありアカウントで再ログイン、または管理者に依頼 |
| プロバイダーエントリーは見えるがOpenAI互換選択肢なし | バージョンでプラグイン実装・命名違い、または先に対応プロバイダー有効化必要 | `OpenAI`、`OpenAI Compatible`、`OpenAI-API-compatible`等の入口確認し、必要ならプラグインやバージョン説明チェック |
| プロバイダー保存失敗 | API Key誤り、またはBase URLカスタム可のタイプ未選択 | OpenAI互換プロバイダー入口に変更し、`sk-...`を再記入 |
| 401 unauthorized | トークン無効、コピーミス、削除済み | トークン再発行・差し替え |
| 403/model not allowed | Difyで選択したモデルがトークンホワイトリスト外 | Crazyrouter管理画面で該当モデル許可設定 |
| 404 | `API Base URL`をルートドメインや完全APIパスで記入 | `https://api.crazyrouter.com/v1`に修正 |
| モデル設定可だがアプリ側エラー | モデル名ミス、コンテキストパラメータ不合理 | `gpt-5.5`に戻し基準認証 |
| ナレッジベースインポート失敗 | チャットモデルは認証済み、Embedding未設定 | Embedding設定単独認証→ナレッジベース再インポート |
| ワークフローコスト急増 | バッチ・長コンテキスト・複数アプリでトークン共用 | トークン分割、クォータ上限設定、モデル範囲縮小 |
| 高度モデル能力の挙動がDify内で不一致 | Difyノードごとモデルパラメータ互換性差 | `gpt-5.5`で基準検証→他モデルへの段階的切り替え |

## パフォーマンスとコスト対策

- ワークフローではまず`gpt-5.5`でテスト、安定後に他モデルを追加
- ナレッジベース初回は少量ファイル導入で召回品質検証→大量登録
- チャット/Embeddingモデルは別でコスト管理し、消費源を特定しやすく
- バッチ・定期・内部テスト環境では厳格なクォータ上限を設定
- 消費急増時、Crazyrouterログでバッチ再試行・ナレッジベースインポート・複数アプリ分トークン共用か確認

## FAQ

### DifyはどのBase URLを記入すべき？

`https://api.crazyrouter.com/v1`を記入してください。

### なぜルートドメインを推奨しない？

DifyのOpenAI互換プロバイダーは通常、OpenAI互換Base URLの記入が求められ、ルートドメインでは認証できません。

### チャットモデルとEmbeddingどちらから設定すべき？

まずチャットモデルを設定し、アプリが正常応答することを確認後、Embeddingを設定します。

### Rerankモデルは直接設定できる？

利用中のDifyバージョンと有効なプロバイダープラグイン次第です。チャットとEmbeddingを先に認証し、必要ならRerankを検討。

### なぜここでチャットモデル一つのみ先に設定を強調？

Difyの問題はプロバイダー・モデル種別・アプリパラメータ・ナレッジベース経路などで同時に発生しやすいです。まず`gpt-5.5`のチャットアプリのみ認証すれば、特定が明確になります。

### Difyでトークン分割が必要？

分割推奨です。開発/本番で分離し、高トラフィック時はチャットとEmbeddingも分けて運用。

<Note>
Difyは「アプリプラットフォーム」「ワークフロープラットフォーム」として活用するのが最適です。チャットフロント系と比べ、プロセスオーケストレーション、ナレッジベース、多環境管理が重視されるため、専用トークン・モデルホワイトリスト・クォータ戦略がより重要となります。
</Note>
